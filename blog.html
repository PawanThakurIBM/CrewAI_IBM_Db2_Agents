10-Agent Airline Delay Management: Enterprise Orchestration with CrewAI and IBM Db2

One flight delay query. Ten specialized agents. A single reviewed operational response. This is how production-grade multi-agent orchestration works — every agent grounded in enterprise knowledge retrieved from IBM Db2, context flowing from agent to agent until a QA-validated brief is ready.

   Written by   Pawan Thakur·Dhruv Chaturvedi Contributors, crewai-tools

CrewAI is one of the fastest-growing frameworks for building multi-agent AI systems — teams of autonomous agents that plan, delegate, and collaborate to complete complex tasks. But agents are only useful if they can access real information. To close that gap for IBM Db2 users, we contributed the IBM Db2 Vector Search Tool to the official crewai-tools library.

The tool is deliberately retrieval-only, which means you keep full control of how documents get into Db2 in the first place. In this article we'll use Haystack and the IBM Db2 integration to build that ingestion side, then hand the resulting tables to a CrewAI crew — but the ingestion layer is yours to choose. LangChain, Langflow, a nightly ETL job, or a plain Python script all work equally well, because the contract between the two halves is nothing more than a Db2 table with a VECTOR column.

What is CrewAI?

CrewAI is an open-source Python framework for orchestrating role-based, autonomous AI agents. Instead of chaining fixed steps together like a traditional pipeline, CrewAI lets you define a crew of agents, each with a role, a goal, and a backstory, and hand them a set of tasks and tools. The agents then plan and reason about how to complete their work, deciding for themselves which tools to call and when.

This is a meaningfully different model from a conventional RAG pipeline. In a pipeline, retrieval happens on every request because a developer wired it that way. In CrewAI, retrieval happens because an agent decided it needed more information to complete its goal. Agents can call a search tool once, several times, or not at all, depending on what the task actually requires.

CrewAI doesn't just retrieve context — it decides when retrieval is even necessary, then reasons over whatever it finds.

Core building blocks

  • Agents — autonomous workers with a role, goal, backstory, and a set of tools they're allowed to use
  • Tasks — units of work assigned to an agent, with a description and an expected output
  • Tools — capabilities an agent can invoke, such as web search, file access, or in this case, semantic search against IBM Db2
  • Crews — a collection of agents and tasks executed sequentially or hierarchically, with agents able to delegate to one another

Two Halves: Ingestion and Retrieval

Every agentic knowledge system splits into two independent halves, and it pays to keep them independent:

Ingestion (write path) Retrieval (read path)
Runs on a schedule or on content change — batch, offline, no agent involved Runs inside an agent's reasoning loop, on demand, one query at a time
Chunks documents, embeds passages, writes rows with their vectors Embeds one question, ranks rows by VECTOR_DISTANCE, returns the top matches
Pick any framework: Haystack, LangChain, Langflow, or your own script DB2VectorSearchTool inside the crew
Owns the table schema and the metadata columns Reads whatever schema ingestion created — never writes

The whole contract between them is three things: the same table, the same embedding model (so the vectors are comparable and the dimensions match), and the same distance metric. Get those three right and the two halves never need to know about each other. We use Haystack below because the IBM Db2 integration makes the write path about fifteen lines — but nothing in the retrieval half depends on that choice.

Swap Haystack for LangChain or Langflow tomorrow and not a single line of the crew changes. The agents only ever see a Db2 table.

Why CrewAI for Enterprise AI Agents?

Enterprise workloads rarely fit a single fixed pipeline. A support request might need a knowledge-base lookup, a policy check, and a summarization step — and which of those steps actually run depends on the question being asked. CrewAI's agent model maps naturally onto this kind of variable, decision-driven work:

  • Role specialization. Different agents can own different responsibilities — one searches, one drafts, one verifies — mirroring how real teams divide work.
  • Tool-driven reasoning. Agents decide when to call a tool like DB2VectorSearchTool, rather than the developer hard-coding a retrieval step into every request.
  • Composable crews. Multiple agents can be sequenced or run hierarchically, letting complex workflows emerge from simple, well-scoped roles.
  • Runs entirely on your infrastructure. With Granite models served by Ollama and Db2 holding the vectors, no document text and no customer question ever leaves your network.

What's been missing for IBM Db2 users is a first-class way to plug enterprise data into that agent loop. That's exactly what the IBM Db2 Vector Search Tool provides.

What You Can Build with CrewAI + IBM Db2 Vector Search

IBM Db2 12.1.2 introduced a native VECTOR data type and the VECTOR_DISTANCE function, which means Db2 can act as a vector store without any additional infrastructure. Paired with CrewAI, that unlocks:

  • Autonomous enterprise support agents that decide on their own when a question requires pulling from the knowledge base stored in Db2
  • Multi-agent research crews, where a search agent retrieves candidate documents and a second agent synthesizes an answer from them
  • Compliance-aware assistants that combine vector similarity with metadata filters (category, region, sensitivity) so agents only ever see the data they're allowed to
  • Hybrid agent workflows where the Db2 tool sits alongside other CrewAI tools — web search, file readers, custom APIs — and the agent chooses which one applies
  • Fully air-gapped copilots for internal teams, backed by whatever enterprise content already lives in Db2, with no separate vector database and no external model calls

Why Agents Need Semantic Search, Not Just a Database Lookup

Imagine an enterprise support agent built with CrewAI. When a user asks a question, the agent first reasons about whether it already knows the answer. If it doesn't, it invokes the DB2VectorSearchTool, which embeds the question, retrieves the most semantically relevant rows from Db2, and hands that context back to the agent. The agent never writes SQL, never knows the table schema, and never has to decide how "close enough" a match is — the tool abstracts all of that away.

That only works well if retrieval is based on meaning rather than exact matches. A traditional WHERE clause can't tell you that "how do I reset my password" and "I'm locked out of my account" are asking about the same thing. Vector search can.

Traditional Database Lookup Semantic Vector Search
Matches exact keywords or predefined fields Matches based on meaning, even with different wording
Requires the caller to know column names and query syntax Requires only natural language — the agent asks a question, not a query
Struggles with unstructured text like support tickets or policy documents Purpose-built for unstructured and semi-structured enterprise content
Filtering is the only way to narrow results Combines similarity ranking with optional metadata filtering
Brittle for autonomous agents — a slightly different phrasing returns nothing Robust for agents, since intent matters more than exact phrasing

Introducing the IBM Db2 Vector Search Tool

DB2VectorSearchTool is a first-class CrewAI tool that performs semantic similarity search directly against IBM Db2 using the native VECTOR_DISTANCE function — no separate vector database required. It follows the same architecture as CrewAI's other retrieval tools, such as QdrantVectorSearchTool and WeaviateVectorSearchTool, so it drops into existing crews with minimal changes.

Features of the tool

  • Native Db2 VECTOR_DISTANCE — similarity search runs inside the database itself, with no external vector index to maintain
  • Six configurable distance metrics — COSINE, EUCLIDEAN, EUCLIDEAN_SQUARED, DOT, HAMMING, and MANHATTAN, whitelisted against Db2's own metric names
  • Bring your own embeddings — pass any callable as custom_embedding_fn and the tool uses it verbatim. That's how we plug in Granite embeddings served locally by Ollama, and how you'd plug in watsonx or anything else
  • Retrieval-only by design — the tool never writes to Db2, so your ingestion framework stays entirely your own choice
  • Metadata filtering via filter_by / filter_value, applied together with vector similarity in a single query
  • Distance-based cutoff via max_distance, so agents don't reason over weakly related results
  • Runtime dependency resolution — ibm_db and ibm_db_dbi are imported lazily on first use, so importing the tool never forces a driver install you don't need
  • SQL injection protection — table, column, and schema names are validated against a strict identifier pattern before ever reaching a query
  • Parameterized queries — user-supplied values are always bound as query parameters, never interpolated into SQL strings
  • Normalized, type-safe JSON responses — a custom encoder safely serializes Decimal, timestamp, and binary values coming back from Db2

Architecture

Part 1 · Getting Airline Knowledge into Db2 with Haystack

Our example is an Airline Delay Management Assistant — a production-grade system where 10 specialized agents collaborate to handle any flight disruption. Before the crew can run, we need to populate IBM Db2 with the airline's enterprise knowledge: SOPs, compensation policies, rebooking procedures, IATA delay codes, regulatory guidelines, and crew manuals. That's the job of the ingestion pipeline.

We use Haystack for ingestion here, but the pattern works identically with LangChain or LlamaIndex — the crew never touches the ingestion layer, so you can swap it out without changing a single agent.

Ingestion Pipeline

Loading 20 airline documents into Db2

The ingestion pipeline discovers every .md file under src/data/, cleans the text, splits it into 512-token chunks with 50-token overlap, embeds with all-MiniLM-L6-v2, and writes documents and vectors to two separate Db2 tables. Splitting and storage are handled by plain Python — no native Haystack Db2 integration is required.

from pathlib import Path
from sentence_transformers import SentenceTransformer
from src.knowledge.db2_document_store import Db2DocumentStore
from src.knowledge.db2_vector_store import Db2VectorStore

class IngestionPipeline:
    """End-to-end ingestion: .md files → Db2DocumentStore + Db2VectorStore."""

    def __init__(self):
        self._data_dir  = Path("src/data")
        self._embedder  = SentenceTransformer("sentence-transformers/all-MiniLM-L6-v2")
        self._doc_store = Db2DocumentStore()   # writes to AIRLINE_KB.DOCUMENTS
        self._vec_store = Db2VectorStore()     # writes to AIRLINE_KB.VECTORS

    def run(self, wipe_first: bool = False) -> dict:
        self._doc_store.connect()
        self._vec_store.connect()

        files  = sorted(self._data_dir.rglob("*.md"))   # 20 docs across 5 folders
        chunks = []

        for path in files:
            text   = _clean_text(path.read_text())
            splits = _split_into_chunks(text, chunk_tokens=512, overlap_tokens=50)
            for i, chunk in enumerate(splits):
                doc_id = _stable_id(str(path), i)       # deterministic sha256 id
                chunks.append({"id": doc_id, "content": chunk, "source": str(path)})

        # Batch-embed all chunks in one pass (32 at a time)
        embeddings = self._embedder.encode(
            [c["content"] for c in chunks],
            batch_size=32, normalize_embeddings=True,
        )

        self._doc_store.write_documents(chunks)
        self._vec_store.write_vectors([
            {"doc_id": c["id"], "embedding": e.tolist()}
            for c, e in zip(chunks, embeddings)
        ])
        return {"files": len(files), "chunks": len(chunks)}

Run it once with python scripts/ingest_knowledge.py and Db2 holds everything the crew will ever need. Nothing here runs at query time — the agents never touch the ingestion layer.

The two Db2 tables it creates

Documents and vectors are stored separately so either can be re-indexed independently:

-- Document text and metadata
CREATE TABLE AIRLINE_KB.DOCUMENTS (
    id      VARCHAR(64)  NOT NULL PRIMARY KEY,
    content CLOB(1M),
    source  VARCHAR(512),
    meta    CLOB(64K)    -- JSON: source_file, chunk_index, total_chunks
);

-- Embedding vectors for cosine similarity search
CREATE TABLE AIRLINE_KB.VECTORS (
    doc_id    VARCHAR(64)   NOT NULL PRIMARY KEY,
    embedding VARCHAR(32000) -- 384-dim float32 serialized as JSON array
);
Using LangChain or LlamaIndex instead? The crew doesn't care. Swap the ingestion layer freely — the only contract is that AIRLINE_KB.DOCUMENTS and AIRLINE_KB.VECTORS are populated with the same embedding model used at retrieval time.

Part 2 · Build the 10-Agent Airline Crew, Step by Step

Now the runtime side. We build the IBM Db2 Search Tool that all 10 agents share, define a representative agent and task, wire up the full crew with context chaining, and expose it over a Server-Sent Events streaming endpoint so the UI can show each agent completing in real time.

Step 01

The IBM Db2 Search Tool — one tool shared by all 10 agents

Every agent calls this tool whenever it needs to look up a policy, SOP, regulation, or procedure. Internally it runs the full Haystack retrieval pipeline: embed → cosine similarity in Db2 → cross-encoder rerank → formatted string. Agents never call Haystack directly.

# src/tools/db2_search_tool.py
from crewai.tools import BaseTool
from src.knowledge.retrieval_pipeline import retrieve

class Db2SearchTool(BaseTool):
    name: str = "IBM Db2 Enterprise Knowledge Search"
    description: str = (
        "Search the airline enterprise knowledge base stored in IBM Db2. "
        "Use this tool whenever you need to look up airline SOPs, compensation policies, "
        "passenger rights regulations, rebooking procedures, airport operations manuals, "
        "crew handling procedures, IATA delay codes, or any internal airline policy. "
        "Input: a natural-language query string. "
        "Output: the most relevant policy / procedure excerpts."
    )

    def _run(self, query: str) -> str:
        """Embed → vector search → rerank → return formatted excerpts."""
        return retrieve(query)

# Singleton shared across all agents
db2_search_tool = Db2SearchTool()

The retrieve() function behind it embeds the query with all-MiniLM-L6-v2, fetches the top-10 nearest vectors from Db2 using cosine similarity, reranks them with cross-encoder/ms-marco-MiniLM-L-6-v2, and returns the top-5 as labelled text blocks the agent can read directly.

Define a specialist agent

Each of the 10 agents follows the same pattern: a tight role, a single-sentence goal, a grounding backstory, and the shared db2_search_tool plus any domain-specific API tool. The LLM is ollama/granite3.3:8b running locally.

Step 03

Define a task with context chaining

Tasks are where context flows. Downstream tasks declare their upstream dependencies via context=[...] — CrewAI injects those completed outputs before the agent starts, so no agent ever asks for information that a previous agent already produced.

# src/tasks/weather_task.py
from crewai import Task
from src.agents.weather_agent import weather_agent

def make_weather_task(flight_query: str) -> Task:
    return Task(
        description=(
            f"Flight delay report:\n\n{flight_query}\n\n"
            "Retrieve current METAR and TAF for both departure and arrival airports. "
            "Then query the IBM Db2 Enterprise Knowledge Search for the airline's "
            "weather operations SOP to classify severity and operational impact."
        ),
        expected_output=(
            "Structured weather assessment: conditions at both airports, 24-hour forecast, "
            "severity classification (Low/Medium/High/Severe), and operational impact statement."
        ),
        agent=weather_agent,
        # No context= here — weather is a first-wave task that reads the raw user query
    )

# Downstream tasks declare their dependencies — the Decision Agent consumes everything:
# make_decision_task(weather_task, flight_task, passenger_task,
#                    runway_task, aircraft_task, rebooking_task)
How context flows in this crew: Weather, Flight, and Passenger tasks run first with only the raw query. Runway and Aircraft tasks receive context=[weather_task, flight_task]. Rebooking receives context=[passenger_task, flight_task]. The Decision Agent receives all six. Compensation receives Decision + Passenger. The Review Agent receives Decision + Compensation. Step 05

Expose it as a Server-Sent Events streaming endpoint

The crew runs in a background thread. Each task callback pushes an AgentEvent into a queue.Queue, and an async FastAPI generator drains that queue as SSE frames — so the browser sees each agent complete as it happens, not in one lump at the end.

# src/api/routes.py  (abbreviated)
import queue, threading
from sse_starlette.sse import EventSourceResponse
from src.api.schemas import AgentEvent

@router.get("/analyze/stream")
async def analyze_stream(query: str, request: Request):
    event_q: queue.Queue = queue.Queue()

    # Crew runs in a background thread — doesn't block the async event loop
    thread = threading.Thread(
        target=_run_crew_with_events, args=(query, event_q), daemon=True
    )
    thread.start()

    async def _generator():
        loop = asyncio.get_event_loop()
        while True:
            if await request.is_disconnected():
                break
            item = await loop.run_in_executor(None, event_q.get, True, 1.0)
            if item is None:      # sentinel — crew finished
                break
            yield {"event": item.event, "data": item.model_dump_json()}

    return EventSourceResponse(_generator())

Each SSE frame carries a structured AgentEvent: step number, agent name, task name, elapsed seconds, and the agent's full output. The final frame has event="final" and carries the Review Agent's approved operational brief. A standard blocking POST /analyze endpoint is also available for non-streaming clients.

Understanding the Tool Response

The _run() method always returns a plain string — the CrewAI contract. The string is a labelled list of the top-5 reranked document excerpts, ready for the agent to read and reason over directly:

[Document 1 — compensation_policy.md]
For delays exceeding 3 hours on EU routes, cash compensation of €250 applies
for flights under 1500 km. Meals and refreshments must be offered after 2 hours.

[Document 2 — flight_delay_sop.md]
When a delay is classified High or Severe, the Operations Control Centre must
be notified within 15 minutes. The duty manager initiates the delay management
checklist and assigns a passenger handling coordinator.

[Document 3 — eu261_2004_regulation.md]
Article 7 of EU Regulation 261/2004 stipulates standardised compensation
amounts based on flight distance and final delay at destination.

When the knowledge base has no relevant documents, the tool returns a single diagnostic string so the agent can surface the gap rather than hallucinating an answer:

[IBM Db2 Knowledge Base]
No relevant documents found for the given query.
Ensure the knowledge base has been ingested via: python scripts/ingest_knowledge.py

The retrieve pipeline behind it runs embed → top-10 cosine similarity in Db2 → cross-encoder rerank → top-5. The reranker (ms-marco-MiniLM-L-6-v2) re-scores the vector hits against the original query string, so the final five are the semantically best passages, not just the nearest vectors. Both models are lazy-loaded on first query and shared across all agents via a module-level singleton — the Db2 connection is opened per-query and closed in a finally block.

Security Features

Because the tool's inputs ultimately come from an LLM's tool call rather than a trusted developer, it's built with the assumption that anything the agent passes in could be adversarial or malformed:

  • SQL identifier validation. Table, column, and schema names must match ^[A-Za-z][A-Za-z0-9_]*(\.[A-Za-z][A-Za-z0-9_]*)?$ before they're allowed anywhere near a query string. That includes the filter_by column an agent chooses at call time.
  • Parameterized queries. Query embeddings and filter values are always bound as parameters — never string-interpolated into SQL.
  • Distance metric whitelist. Only the six Db2-supported metric names are accepted; anything else raises a validation error before a connection is even opened.
  • Empty-query rejection. A blank or whitespace-only query short-circuits with a structured error rather than burning an embedding call and a database round trip.
  • Explicit connection lifecycle. Every call opens a fresh connection and closes it in a finally-style cleanup, including on error paths, so failed searches don't leak connections.
  • Nothing leaves the network. all-MiniLM-L6-v2 and the cross-encoder run locally via sentence-transformers, granite3.3:8b runs on Ollama, and Db2 holds the vectors — no document text and no user query is ever sent to an external API.

Best Practices

  • Define the embedding function once and import it everywhere. One module holding the model name, the query prefix, and the dimension is the cheapest insurance against the two halves drifting apart.
  • Re-embed everything when you change models. Switching embedding models means re-running ingestion over the whole corpus. Vectors from two different models are not comparable, and Db2 has no way to tell you that.
  • One tool instance per corpus, with a distinct name. Give each instance a name and description that says what lives in that table and when to reach for it — that description is the only thing the agent has to go on.
  • Return the id column. It costs a few tokens and buys you citations, which is what makes a grounded answer auditable.
  • Set a max_distance for autonomous agents. Without a cutoff, an agent can end up "reasoning" over irrelevant rows just because they were the closest of a bad set. Tighter corpora (policy) deserve a tighter cutoff than broad ones (tickets).
  • Tune chunk size at ingestion, not retrieval. If agents keep getting fragments that end mid-procedure, the fix is a larger split_length or more overlap in the indexing pipeline — no change to the crew required.
  • Say "search" in the task description. Agents call tools based on how well their role, goal, and task match — a task that says "review the findings" often produces no tool call at all, while "search the policy corpus and cite the document id" reliably does.
  • Use metadata filters for anything security- or compliance-sensitive — and back them with a least-privilege Db2 credential rather than trusting the filter alone.

Production Considerations

Ingestion is your pipeline, on your schedule. The tool never writes to Db2, so re-indexing, deletions, and freshness are the ingestion layer's job. Whether that's a Haystack pipeline on a cron, a Langflow flow, or a nightly batch job, the crew keeps working unchanged as long as the table and the embedding model stay put.

Connection lifecycle per call. Each invocation opens and closes its own Db2 connection. A four-agent crew like the one above can easily make six to ten searches per run, so plan your Db2 connection limits accordingly, or front the database with a connection pooler.

One embedding call per search. Every tool call embeds its query before it touches Db2, so more agents searching means more Ollama requests. That's cheap when the model is local, but it is still latency in the agent's loop — size the Ollama host for the concurrency your crews actually generate, and set a sensible timeout on the embedding call so a stalled request surfaces as a structured error rather than a hung crew.

Least-privilege database credentials. Give the crew a Db2 user with read access to exactly the tables and views the agents are allowed to search — nothing more. Ingestion needs write access; retrieval never does, so use two different credentials.

Monitor success: false responses. Because errors come back as structured JSON rather than exceptions that bubble up, log and alert on error_type values in production so connection or embedding failures don't silently degrade agent quality.

Frequently Asked Questions

Q1. What is CrewAI?

CrewAI is an open-source Python framework for building multi-agent AI systems. It organizes work around role-based agents, tasks, and tools, and lets agents reason about which tools to call rather than following a fixed pipeline.

Q2. What is the IBM Db2 Vector Search Tool?

DB2VectorSearchTool is a CrewAI tool that lets agents perform semantic vector similarity search directly against IBM Db2 using the native VECTOR_DISTANCE function, with no separate vector database required.

Q3. Does the tool handle ingestion too?

No, and that's deliberate. The tool is retrieval-only. Chunking, embedding, and loading documents into Db2 is a separate job that you run on your own schedule with your own framework.

Q4. Do I have to use Haystack for ingestion?

Not at all. We use Haystack here because the IBM Db2 integration makes the write path very short, but LangChain, Langflow, or a plain Python script that embeds text and runs an INSERT all produce something the tool can read. The agents only ever see a Db2 table.

Q5. Which embedding model does this project use?

The ingestion pipeline and the retrieval pipeline both use sentence-transformers/all-MiniLM-L6-v2 (384-dimensional, normalized cosine). The retrieval step then reranks the top-10 vector hits with cross-encoder/ms-marco-MiniLM-L-6-v2 before returning the top 5. Both models run locally via sentence-transformers — no Ollama required for embedding.

Q6. Why use a cross-encoder reranker on top of vector search?

Cosine similarity on dense vectors is fast but imprecise — it ranks by embedding proximity, not by how well a passage actually answers the query. The cross-encoder reads the query and each candidate passage together and produces a true relevance score, making the final top-5 significantly more accurate than the raw vector top-10. The cost is acceptable because reranking only runs on 10 passages, not the whole corpus.

Q7. Do I need a separate vector database?

No. If you're on IBM Db2 12.1.x or later with native VECTOR support, Db2 itself acts as the vector store for both the write and the read path.

Q8. Can multiple agents search Db2 in the same crew?

Yes — that's the recommended pattern for anything non-trivial. A single instance can be shared across agents, or you can build one instance per corpus and hand each specialist the one it needs, as shown in Steps 03 and 04.

Q9. How does an agent choose between two Db2 tools?

Purely from the name and description you give each instance. Both are ordinary constructor arguments, so name them after the corpus they search and describe when to use them.

Q10. Can I filter on Haystack metadata?

Not directly — Haystack stores metadata as JSON in a single meta column, while filter_by expects a real column. Expose the fields you filter on through a view, as in Step 06, or write them as proper columns from a custom ingestion job.

Q11. Is the tool safe against SQL injection?

Yes. Table, column, and schema identifiers are validated against a strict pattern before use, distance metrics are checked against a whitelist, and all values are passed as parameterized query arguments rather than string-interpolated.

Q12. Is this suitable for production use?

Yes. The tool includes identifier validation, parameterized queries, a metric whitelist, and type-safe response serialization, following the same architecture as other production CrewAI vector search tools such as the Qdrant and Weaviate integrations.

Conclusion

The Airline Delay Management Assistant demonstrates that multi-agent orchestration is not complicated to reason about if you keep the responsibilities clean. Ingestion is a one-time batch job — 20 airline documents, split at 512 tokens, embedded with all-MiniLM-L6-v2, stored in two Db2 tables. The crew is 10 agents, each owning one slice of the problem, chained by explicit context=[...] dependencies so every downstream agent builds on what came before. The single db2_search_tool shared by all of them means no agent ever hallucinates a policy — it looks it up. granite3.3:8b on Ollama does the reasoning, the whole stack runs on your own infrastructure, and a FastAPI SSE endpoint makes every agent's completion visible in real time. That's the full picture — from a raw delay report to a QA-reviewed operational brief, entirely on-premise.
